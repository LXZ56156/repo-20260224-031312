# 产品基准与候选路线

> 更新时间：2026-08-14。用户已决定产品先以当前线上版本为基准；本文据此重新定义其他路线的角色。

## 结论

产品基准固定为正式线上版本 `6.1.2-e60d827-r3`，客户端源码身份为 `55bfc4f`。这是当前唯一可用于判断“现有产品行为”的事实基准，也是后续产品工作的默认起点。

1. 线上版本：产品基准和新工作的默认分支起点。
2. `score-only UI`：已批准的单点候选，可按需要相对线上基准重新评审，不自动成为基准。
3. `协作打水 V2`、`share activity + local ops`：保留为候选能力与研究成果，默认不并入产品基准。
4. Next-Gen：继续暂停，只保留历史证据。

## 为什么这样排

| 路线 | 已有价值 | 当前缺口 | 当前角色 |
|---|---|---|---|
| 当前线上版本 | `6.1.2-e60d827-r3` 已由用户确认正式发布；客户端 633 个文件与 `55bfc4f` 一致 | 云端 rollout 不能从客户端版本推断 | 唯一产品基准；使用干净 PRODUCTION 建立 ACTIVE |
| score-only UI | `51fe6dc` 是聚焦、已批准的 schedule 视觉候选，变更面小；branch 与恢复 bundle 已归档 | 相对线上版本仍是未确认发布的增量 | 单点候选与视觉对照；使用前重新确认，不默认叠加 |
| 协作打水 V2 | `e60d827` 与后续未提交成果已完整归档并验证可恢复 | collection/index/config、部署、迁移、canary、preview/upload 均未完成 | 受保护候选；不作为当前产品基准或默认下一步 |
| share activity + local ops | `fb8ea52` 与 `006205c` 提供活动归因、事件采集和本地运营观察能力；相关开关默认关闭 | 集成基线不同；云函数曾部署不能证明客户端已接入或产品已上线 | 可选配套能力；只有具体需求获批后才从线上基准重新评估接入 |
| Next-Gen | 保存了大量设计、架构和实验资产，四棵树均已完整归档并验证可恢复 | 路线已暂停，且历史视觉方向曾被否决 | 归档研究库；只按具体问题复用，不恢复为并行主线 |

## 后续执行合同

1. 新产品任务从干净 PRODUCTION（`55bfc4f`）创建唯一 ACTIVE，不从 `METADATA_ROOT` 或归档恢复目录直接开发。
2. 先按线上版本复现和验收现状，再提出单点变化；用户可见变化仍须先审批。
3. 需要候选路线中的能力时，只提取与已批准需求直接相关的最小差异，并重新做兼容与回归审计；不得整分支合并。
4. Git push、兼容云部署、小程序 preview/upload 和正式发布继续分别记账、分别遵守授权边界。

## 不建议的组织方式

- 不把某个本地 RC、已批准 overlay、Git push 或云函数部署解释为线上产品基准已经变化。
- 不为了“赶上本地进度”把多个候选分支先合并，再回头核对线上行为。
- 不从暂停的 Next-Gen 归档直接抽取整批代码；只能围绕已确认问题做小范围、可验证复用。
