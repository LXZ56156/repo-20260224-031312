## 四 P1 数据安全与一致性

A1 五个赛事写入口的事务边界风险
位置：cloudfunctions/startTournament/index.js:293 附近；addPlayers/index.js:258；removePlayer/index.js:100；updateSettings/index.js:144；setReferee/index.js:63。
证据：五处仍在事务回调使用 where({_id,version}).update；固定 SDK 的请求捕获证实该更新不携带 transactionId。
影响：业务更新与请求日志、提交失败或回滚可能不在同一原子边界。版本条件仍存在，不能称为“完全没有并发控制”。
建议：在事务中读权威文档后使用同事务 doc 更新，保留角色、版本、幂等日志；不要只凭内存 mock 的事务行为验收。
验收：精确 SDK 请求具有一致事务 ID；再于独立云测试环境验证日志写失败、冲突重放和回滚。当前生产安装包与发生率未验证。

A2 旧版 V1 创建竞态覆盖账本
位置：cloudfunctions/waterSession/index.js:184–214。
证据：慢请求在“不存在”检查后停住，快请求创建并成功记账，再放行慢请求。2 人、1 条记录、版本 3 变成 1 人、0 条记录、版本 1；请求均返回成功。
范围：仍可走未迁移 V1 create 且写开关允许的兼容路径，不泛化到 V2 独立新建。
建议：存在性检查与首次创建原子化；已存在返回权威现状，保留旧链接访问，不通过删除兼容数据解决问题。
验收：两个创建并发、创建与录入交错，原记录和版本不得倒退。

建议把可重复的集合准备移入受控初始化或做可靠的进程内缓存。赛事 scoreLockRevision 写入是为了与提前收赛形成冲突，不能直接删掉；是否值得拆分锁竞争协调文档，应先测量真实冲突和 watch 成本。

D9 跨调用重复生成同一分享码  P3 观察
同一赛事/环境的两次服务端调用，均生成二维码并上传。客户端已有进程内缓存，但不覆盖跨设备或重启。
