## 已确认问题

### F1 / P2：设置页同步会覆盖未保存编辑，失败重试会发送还原后的旧值

**代码证据：**

- `miniprogram/pages/settings/index.js:136` 的 `applyTournament()` 每次构造完整设置状态；第 144 行直接 `setData(viewState)`。
- `miniprogram/pages/settings/settingsViewModel.js:326` 起的返回对象包含 `name`、`editM`、`editC`、`pointsPerGame`、结束条件等编辑字段；没有按未保存字段做合并。
- `miniprogram/pages/settings/settingsActions.js:324` 保存失败后立即 `await this.fetchTournament(...)`；第 326 行设置的重试调用 `saveSettings({ clientRequestId })`，再次从已经被还原的 `this.data` 读取输入。

**触发：**管理员正在设置草稿赛事，期间其他成员加入引起新文档同步，或切后台后返回触发 fetch；另一条路径是保存失败后 fetch 成功。

**本地实测：**调用真实 Page 方法，所有数据与网络均为 stub：

```json
{"case":"settings live roster update","edited":{"name":"未保存的新名称","points":11},"afterRefresh":{"name":"原始名称","points":21}}
{"case":"settings retry after rejected write and remote refresh","firstName":"目标名","retryName":"原名","sameClientRequestId":true}
```

这不是仅有显示回跳：第一次失败后点击“重试上次操作”，实际请求内容已经改变，却复用了同一个请求编号。服务器如何处理同编号不同内容应由后端审查核实；前端丢失原始重试意图已独立证明。

**影响：**主办者修改白做；在未察觉回跳时可能保存旧参数；“重试上次操作”与实际操作不一致。

**建议：**保留未保存字段，仅同步名单、权限和约束；权限或赛事状态变化仍及时生效。失败重试保留原始 payload 与对应 clientRequestId，用户主动修改内容后再形成新操作。增加两条直接回归：名单更新不覆盖编辑、失败重试保持原始内容。

**验证状态：**本地复现通过；未执行真实赛事编辑或生产写入；未统计线上触发量。

### F2 / P2：赛程页身份初始化只读一次，登录迟到后录分入口不会恢复

**代码证据：**

- `miniprogram/pages/schedule/index.js:375` 在 `onLoad()` 一次性读取 `this.openid`。
- `miniprogram/pages/schedule/index.js:411` 的 `onShow()` 刷新赛事和 watch，但不刷新身份。
- 第 454 行始终用 `this.openid` 计算 `canEditScore`；第 462 行据此决定是否显示“继续录分”。
- `miniprogram/pages/share-entry/index.js:106` 并行启动 `primeViewerIdentity()`；第 212 行身份等待只门控 `draft`。运行中赛事可以在身份解析完成前，经第 326/447 行进入赛程。

**触发：**无本地 openid 的冷启动，打开运行中赛事分享后，在登录完成前进入赛程。管理者或允许录分的参赛者会先被当作无身份用户，后续 app/cache 身份到达也不会更新赛程页面实例。

**本地实测：**用真实赛程 Page 执行 `onLoad → applyTournament → app/cache 写入登录结果 → onShow → applyTournament`：

```json
{"case":"late auth on schedule","appOpenid":"u_admin","pageOpenid":"","canEditScore":false,"nextAction":""}
{"case":"same doc with resolved identity","canEditScore":true,"nextAction":"继续录分"}
```

**影响：**合法用户缺少录分入口；刷新赛事本身不能恢复，需要重建页面。不是越权写入问题，服务器权限仍需独立检查。

**建议：**赛程页接入已经在分享入口/排名页使用的身份恢复思路；登录完成后重新计算权限，显示或隐藏时防止迟到回写。补一条延迟登录回归。match/settings 也存在只在 onLoad 读取 openid 的形态，可在修复中确认实际进入路径，不能凭相似代码直接断言已发生同类线上故障。

**验证状态：**本地权限状态复现通过；未用真机模拟冷启动慢网，未证明线上发生率。

### F3 / P2：赛程错误页“返回首页”没有事件处理函数

**代码证据：**`miniprogram/pages/schedule/index.wxml:182` 绑定 `bindtap="goHome"`，但赛程 Page 实际定义及其展开混入均无 `goHome` 方法。

**本轮检查：**依次加载 app.json 注册的全部 15 个 Page，并检查同目录 WXML 的 287 处静态事件绑定；发现 1 处缺失，正是该按钮。其他 286 处静态绑定解析到函数。动态表达式、组件内部模板和真机事件分发不在该数量内。

**触发：**无效赛事、已删除赛事或加载失败，用户点击错误态“返回首页”。

**影响：**错误后的恢复按钮无效。已有原生返回能力不能替代页面明确提供的按钮。

**建议：**增加调用 `nav.goHome()` 的 Page 方法；补该错误态点击回归即可，无需重做页面。

**验证状态：**WXML 与运行时 Page 定义交叉检查确认；未启动 DevTools 点击，未更改生产。

## 性能与验收缺口

1. **真机验收仍未闭合。** current.md 明确：迁移后 DevTools 新路径会话未重绑，430px、完整交互、大字体以及最终人工验收未完成。本轮没有启动前台预热或用历史截图替代新证据。可在用户已有手机会话中优先验收分享进入→配置→录分→回看，以及打水新增/更正/撤销的少量关键状态。
2. **主包优化应以实际发布包和启动耗时衡量。** app.json 无 lazyCodeLoading、subPackages 为空；上次官方上传回执为 1,138,707 字节，质量工具同时报告较大的分析体积。不能把分析体积 6.5 MB 当成真实发布主包。本轮未重跑打包/质量上传，也未测首屏 P50/P95。先确认低端机启动及大赛事 setData 成本，再决定按需加载或拆包。
3. **长赛事同步成本待量化。** 首页一次拉最多 20 份赛事文档；赛程基于完整 rounds 重建展示状态；轮询降级最低约 1.5 秒取整份赛事文档。存在可观测的成本路径，但没有生产体积、读量与用户停留数据之前，不宣称当前已是性能瓶颈。
4. **测试覆盖有数量，仍有边缘缺口。** 当前设置异步测试会将 applyTournament 替换成只保存 doc 的 stub，能验证请求序列，但无法验证 F1 的真实编辑状态；赛程常用 fixture 在进入时已有 openid，不能覆盖 F2。此次事件绑定普查发现 F3，建议保留一项简单的事件合同检查或局部回归，避免堆叠与实现同构的测试。
